## Introdução

Em agosto de 2026 eu me inscrevi pro Code Academy, curso de programação avançada fornecido pelo instituto 3C. Passei na entrevista e comecei a estudar. O objetivo central do curso é fornecer preparo para se tornar um desenvolvedor full-stack, ensinando como usar tecnologias essenciais de desenvolvimento como Docker e Git, a programar em PHP e laravel, noções básicas do que é um CRUD, uma API-REST, noções de Bancos de Dados relacionais, programação orientada a objetos, MVSC e afins. Além de instruir os alunos a como adotar uma postura profissional em ambientes de trabalhos.

Como projeto final para testar todas as habilidades adquiridas no curso, foi pedido para que se desenvolvesse um site de E-Commerce seguindo uma certa documentação onde estava descrita as regras de negócio e funcionalidades que deve ter no sistema. O tema era de livre escolha.

## Tema

Para me poupar um pouquinho de tempo, eu resolvi reaproveitar o que eu tinha feito no Projeto Integrador I na faculdade. Algumas telas já estavam feitas e a modelagem de banco de dados também, precisando só ajustar o que fosse desnecessário.

O tema desse projeto era fazer um site de E-Commerce com foco em centralizar e facilitar o acesso de alternativas acessíveis de controles de video games, para que qualquer pessoa possa jogar independente da deficiência física portada.

## Regras de negócio

Não vou descrever todas, mas as princípais regras de negócio que foram exigidas foram as seguintes:

- O usuário autenticado só pode ter um carrinho.
- Quando um produto já estiver no carrinho, se adicioná-lo novamente a quantidade soma.
- A quantidade do produto num pedido ou carrinho não pode ultrapassar o estoque.
- Pedidos congelam o preço.
- Ao fazer login ou cadastro, se o front-end mandar um carrinho de visitante, ele deve fundir com o carrinho dessa conta.
- Produto presente só no carrinho de visitante deve ser adicionado. E se já tiver no carrinho do usuário, a quantidade deve ser somada.
- O usuário deve ser avisado se a quantidade máxima for excedida durante a fusão.
- O cálculo de total deve ser feito no servidor.
- A criação de um pedido decrementa a quantidade no estoque, isso deve ser feito numa transação que retorna a quantidade ao normal se falhar.
- Se o pedido for cancelado, a quantidade volta ao estoque.
- Existe ordem para o status do pedido: aguardando pagamento → pago → enviado → entregue; e cancelado a partir de aguardando pagamento.
- Não deve usar ponto flutuando pro calculo de preços. Sempre usar decimal (10, 1).
- O produto que já pertencer a um pedido não pode ser excluído, usa-se apenas exclusão lógica nesse caso. (mais pra frente você vai ver que eu usei exclusão lógica pra tudo não só pra quando o produto tiver num pedido)

### Migrations

Durante o curso do Code Academy nós tivemos uma atividade chamada Work Days. Nela, foram formados dois grupos pra desenvolver o Projeto Final durante três dias. Cada grupo tinha um aluno que foi atribuído o cargo de Tech Lead, ele organizava as tarefas que cada membro da equipe devia fazer. Eu fui um deles. Obviamente foi tudo feito com IA pra poder dar tempo de fazer a atividade.

O projeto que precisamos desenvolver foi o próprio Projeto Final, já que estava bem documentado. Foi pedido somente para não utilizar nenhum framework, ou seja: sem VUE ou semelhantes pro Front e sem Laravel, só PHP pro Back. Também foi pedido para que não tenha mesclagem do carrinho, uma das regras de negócio do projeto final. No fim, saímos da atividade com uma versão em pequena escala do projeto final.

Já que eu já tinha a modelagem teoricamente pronta, eu só reaproveitei as migrations dessa atividade e alterei para seguir a modelagem atual.

Pontos de destaque que foram cobrados durante a apresentação final:

- O que é constrained?
  Constrained é o que impede que um dado invalido seja preenchido naquele campo se não for da tabela desejada. Determina se vai ter alguma regra ou não pra quando algo acontecer com o dado. Na hora eu não soube responder kk...
- Como que o index funciona?
  Esse eu não soube justificar o uso além de dizer que facilita na ordenação pelo campo especificado, tipo: `$table->index('category_id');`. Nesse caso é facilitado a ordenação pela categoria que ele pertence.
  Mas é meio por aí mesmo, ele torna mais rápido a consulta no banco de dados.

Acho que foi só isso...

Alguns outros pontos de destaque:

- A única coisa que diferencia as migrations de usuárias das que já foram criadas por padrão pelo laravel é esse campo: `$table->enum('role', ['client', 'admin'])->default('client');`, que determina a role do usuário.
- Nas migrations de Produtos, `$table->foreignId('category_id')->constrained()->restrictOnDelete();` é interessante pois impede que o produto seja excluído se tiver alguma categoria.
- `$table->integer('stock')->default('0')->unsigned();` é interessante pelo `->unsigned()` que faz com que o valor nunca seja negativo.
